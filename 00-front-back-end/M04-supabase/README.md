# 모듈 — Supabase 데이터베이스 입문

> 상태: 초안

## 목적

초보자가 Supabase(PostgreSQL 기반 백엔드)를 이용해 아주 간단한 데이터베이스(할 일 목록 앱)를 만들고, 데이터를 저장·조회하는 전체 흐름을 직접 경험해본다. 특히 2025~2026년에 걸쳐 바뀐 **새 API 키 체계**와 **기본 보안(RLS) 정책**을 정확히 이해하고 "연결(Connect)"하는 부분에서 실수하지 않는 것을 목표로 한다.

## 무엇을 만드나요?

- Supabase 프로젝트 생성 (GitHub 계정으로 가입 ~ 프로젝트 생성)
- Table Editor로 `todos` 테이블 만들기
- RLS(Row Level Security) 정책을 직접 추가해서 데이터 접근 허용하기
- Connect 창에서 Project URL과 새 Publishable Key를 정확히 찾아 복사하기
- 설치 없이 브라우저에서 바로 실행되는 `index.html` 하나로, 할 일을 추가하고 목록을 불러오는 기능 구현

코딩 경험이 거의 없어도, GUIDE.md의 단계를 순서대로 따라가면 완성할 수 있도록 구성했다. Firebase 버전과 같은 "할 일 목록" 예제를 사용하므로, 두 서비스가 개념적으로 어떻게 다른지 비교해보기에도 좋다.

## Firebase와 무엇이 다른가요?

- Firebase(Firestore)는 문서형 데이터베이스(컬렉션, 문서)이고, Supabase는 관계형 데이터베이스(테이블, 행)다. 그래서 "컬렉션"이 아니라 "테이블", "문서"가 아니라 "행(row)"이라는 용어를 쓴다.
- Firestore는 `collection()`, `addDoc()` 같은 함수 기반, Supabase는 `.from("테이블명").select()/.insert()`처럼 SQL 스타일의 체이닝 함수로 데이터를 다룬다.
- **기본 보안 방향이 정반대다.** Firebase의 "테스트 모드"는 일정 기간 동안 기본적으로 모두 허용하고 나중에 잠근다. 반면 Supabase는 대시보드에서 테이블을 만드는 순간 RLS가 자동으로 켜져서 **기본적으로 전부 차단**되고, 개발자가 정책(Policy)을 직접 추가해야 열린다. 초보자가 가장 자주 막히는 지점이라 GUIDE.md의 3단계에서 별도로 다룬다.
- **API 키 체계가 바뀌는 중이다.** 예전에는 `anon`(공개용) / `service_role`(서버 전용) 키 두 종류였지만, 지금은 `sb_publishable_...`(브라우저·앱용) / `sb_secret_...`(서버 전용) 키로 넘어가는 과도기다. 옛날 `anon`/`service_role` 키는 2026년 말 삭제 예정이다. 옛날 자료를 보고 따라 하다가 구식 키 이름만 찾다 헤매는 경우가 많아 GUIDE.md 4단계에서 Connect 창 사용법을 자세히 짚는다.
- 둘 다 웹페이지에서 직접 접속 가능한 백엔드 서비스라는 점, 보안 규칙(정책)으로 접근을 제어한다는 점은 동일하다.

## 품질 기준

- 실제로 브라우저에서 동작하는 예제 코드가 첨부되어야 한다.
- 코드를 몰라도 복사·붙여넣기만으로 결과를 볼 수 있어야 한다.
- 각 단계마다 "성공했는지 확인하는 방법(체크리스트)"이 있어야 한다.
- API 키를 다루는 단계에서는 반드시 "브라우저에는 publishable 키만, secret 키는 절대 넣지 않는다"는 경고가 포함되어야 한다.
