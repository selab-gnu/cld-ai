# 문서화 규칙 (todo-app)

이 저장소에서는 코드와 문서를 함께 관리한다. 아래 문서 지도와 규칙을 지킨다.

## 문서 지도

| 문서 | 위치 | 누가 원본을 쓰나 | 관련 스킬 |
|---|---|---|---|
| 요구사항 목록 | `docs/requirements.md` | 사람 (에이전트는 제안·정리) | `requirements` |
| 설계 결정 기록 (ADR) | `docs/adr/NNNN-제목.md` | 사람 (에이전트는 초안) | `adr` |
| 아키텍처 그림 | `docs/architecture/overview.md` | 에이전트가 코드에서 생성, 사람이 검토 | `architecture` |
| API 명세 | `docs/api/openapi.yaml` | 명세가 원본. HTML은 생성물이라 커밋하지 않는다 | `api-docs` |
| 사용자 매뉴얼 | `docs/manual/` | 에이전트 초안, 사람 검토 | `user-manual` |
| 이슈 보고서 | `docs/issues/NNNN-제목.md`, `.github/ISSUE_TEMPLATE/` | 재현한 사람 (에이전트는 정리) | `bug-report` |
| 변경 기록 | `CHANGELOG.md` | 에이전트 작성, 사람 검토 | `doc-sync` |

## 규칙

1. **코드를 바꾸면 같은 작업 안에서 관련 문서도 고친다.** 작업을 끝내기 전에 `npm test`와 `npm run docs:check`를 실행해 둘 다 통과시킨다. 어떤 문서를 고쳐야 할지는 `doc-sync` 스킬을 따른다.
2. **새 기능은 요구사항부터.** 구현 전에 `docs/requirements.md`에 요구사항을 추가하고(상태 `승인`), 구현과 테스트가 끝나면 상태를 `구현됨`으로 바꾼다. 그 요구사항을 검증하는 테스트 이름 앞에는 `[REQ-xxx]`를 붙인다.
3. **요구사항을 마음대로 확정하지 않는다.** 코드에서 추정한 요구사항은 상태를 `제안`으로 적고 사람에게 확인받는다. 요구사항을 지우거나 의미를 바꿀 때도 먼저 묻는다.
4. **되돌리기 어려운 설계 결정은 ADR로 남긴다.** 저장 방식, 데이터 형식, 삭제 정책, 번호 매기기 규칙처럼 나중에 바꾸기 어려운 결정을 내리게 되면 `adr` 스킬로 초안(상태 `제안`)을 쓰고 사람의 확인을 받는다. 기존 ADR과 어긋나는 변경은 구현하기 전에 먼저 묻는다. `승인`된 ADR의 본문은 고치지 않고, 바꿔야 하면 새 ADR을 쓰고 옛 ADR의 상태를 `대체됨`으로 바꾼다.
5. **API를 바꾸면 명세도 바꾼다.** 경로, 요청, 응답, 오류 코드를 바꾸면 `docs/api/openapi.yaml`을 함께 고치고 `npm run docs:api:lint`를 통과시킨다.
6. **매뉴얼에는 실제로 실행해 본 명령과 출력만 쓴다.** 추측으로 출력 예시를 만들지 않는다.
7. **문서에 추측을 쓰지 않는다.** 코드에서 확인한 사실에는 근거 파일 경로(예: `src/todo.js`)를 함께 적고, 확인하지 못한 내용은 "확인 필요"로 표시한다.
8. **버그를 발견하면 고치기 전에 보고서부터 쓴다.** `bug-report` 스킬의 양식으로 `docs/issues/`에 남긴 뒤 수정한다.
